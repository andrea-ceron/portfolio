Microservices Architecture

The Kafka Utility Library: Ensuring Asynchronous Resilience

My microservice architecture relies on a shared utility library, Kafka.Utility, which centralizes all asynchronous communication logic and ensures a consistent, event-driven architecture across the system. This library provides a unified approach for creating and managing all necessary Kafka Clients (Admin, Producer, and Consumer) through a Dependency Injection setup. Crucially, the library implements advanced patterns for reliability and resilience:

Key Features and Resilience

Reliable Production (Transactional Outbox): Message production is guaranteed via the Transactional Outbox Pattern. The ProducerServiceWithSubscription first records the message in a database table (TransactionalOutbox) before publishing it to Kafka, ensuring data integrity and consistency between the service's state and its external events.

Asynchronous Consumption : Consumption is managed by the ConsumerServiceWithSubscription, which asynchronously reads messages and maps them to specific business logic via the OperationMessageHandler.

Inter-Service Coherence : The library defines various operation types, including dedicated Compensation Operations (e.g., Compensate Delete), used solely to ensure inter-service coherence in the event of processing failures, adhering to distributed transaction principles.

Error and Resilience Management: Resilience is secured by a Circuit Breaker implementation, which automatically retries failed message execution a predetermined number of times. Centralized error handling is provided via the ErrorManagerMiddleware.

Customer Manager Microservice

The Customer Manager microservice is the system's client-facing domain, responsible for all interactions related to customers. Its core responsibility is managing customer data (client master files) and financial records, including invoice registration. To maintain operational awareness, it holds a localized copy of the finished product catalog, which is synchronized and maintained by the Stock Manager microservice.

Stock Manager Microservice

The Stock Manager is responsible for the finished product lifecycle and production management. This service oversees the manufacturing process, defining which raw materials are required for each finished product. While it defines these material needs, it relies on the Purchase Manager to manage the raw material inventory and procurement, ensuring separation of concerns within the supply chain.

Purchase Manager Microservice

The Purchase Manager handles the external supplier relationship domain. Its responsibilities include managing supplier master files, tracking raw materials associated with those suppliers, and processing all necessary purchase orders. This service acts as the source of truth for all incoming materials required to support the Stock Manager's production demands.

Communication Patterns

Inter-service communication utilizes a dual approach to ensure efficiency and data consistency:

Asynchronous Communication (Kafka): This pattern is employed for event notification and data synchronization across services. Specifically, the registration of a new raw material (by Purchase Manager) or a new finished product (by Stock Manager) triggers a Kafka message to update the relevant service (Stock Manager and Customer Manager, respectively). This ensures eventual consistency with minimal coupling.

Synchronous Communication (HTTP): This pattern is reserved for direct, transactional processes such as the product creation workflow. If a client places an order that depletes the finished product stock, the Customer Manager initiates an HTTP request to the Stock Manager to create more product. This process is cascaded down to the Purchase Manager if raw materials are insufficient, and the final order fulfillment status propagates back up the stack.

This architecture was designed to directly confront two key distributed challenges: maintaining data consistency across database instances and managing systemic instability. I ensured reliability using the Transactional Outbox Pattern within the Kafka Utility Library to manage eventual consistency. Furthermore, system resilience against failures is guaranteed by implementing a Circuit Breaker.
