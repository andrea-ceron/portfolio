The Documentation Process

Introduction

This process is introduced in order to guarantee maintainability and clarity for both present and future internal team membres (including myself) as well as external programmer that might interact with the code.

Based on the type of the project (private or open) different type of documentation will be required.

Project Launch Steps Overview

This documentation explains comprehensively the steps that are required in order to run succesfully the code. This piece of documentation is supposed to ease the understanding phase of all the programmers that are interested to run the code base referenced. The degree of details included span from a very precise (complex projects or prototypes) to few lines long ducumentation (for easy projects to run)

The What

The final documentation that will be created at the end of the process will be a mix of different artifacts. All the artifacts are supposed to complement each other and provide a complete understanding for a specific domain. For instance, UML diagrams aim to depic relational, temporal and object interaction while readme files are instead used to setup instructions, quick user guides or also gather and specify the requisites.

When

Saying that there is a specific time span within the development process that is strictly allocated to designing this artifacts would be a blatant lie. What instad is sure is that while this activity is mainly included within the design phase, slight changes during the developing process could occur forcing to alter the artifact completed till that moment.

How

The documentation process is supposed to give a full illustration of what the end product is and does without looking at the code. This means that not only UML diagrams associated to the design phase will be included, but also the artifact that will lead to that same phase (requirement analysis, Use Case Diagram, Requirement Traceability Matrix). Once those prerequisites are completed I dive into the design phase that will produce diagrams that depic the full system at different levels of granularity.

First I start building the artifacts from the highest level of abstraction. Once those artifacts are completed I zoom in trying to define each component that is part of that previous abstacted element. If by zooming in I'm able descend to the lowest level of abstraction required for the developing process, then I terminated my desing phase for that specific branch, if instead I'm not meeting it I will have spotted a module that can be analyzed as it's parent component. The result of it will be a complete UML documentation that will fully explain any relation among any component at any level of abstraction.

This approach guarantees that new team members can achieve rapid onboarding, development is executed with unambiguous clarity, and the project remains maintainable and secure for years to come. Ultimately, strong documentation translates directly into high-quality code and highly efficient teams.
